### Saturations de boucle d'outils

Deux mécanismes distincts sont journalisés sous des libellés proches ; ils ne
mesurent pas la même chose et il faut les distinguer :

**a) Saturation dure — `max_tool_iterations` atteint** (`"Limite d'appels
d'outils atteinte, arrêt du cycle."`, `graph_nodes.py::should_continue`) :
**66 occurrences** au total sur l'ensemble des logs, concentrées à 40/66 dans
la seule journée du 2026-05-20 (log de 625 lignes, le plus volumineux du
dossier — vraisemblablement une session de test intensive), le reste dispersé
entre le 2026-05-10 et le 2026-06-29. **Zéro occurrence** dans les logs les
plus récents (2026-07-28, 2026-08-05, 2026-08-15, 2026-08-16).

**b) Courts-circuits préventifs** (optimisation `8fb1f09` du 2026-05-18,
« court-circuit ReAct sur saturation de contexte pour réduire P90 ») :
« Court-circuit ReAct » (≥ 2 itérations et ≥ 2 500 caractères de sortie
d'outils cumulés) — **164 occurrences**, concentrées entre le 2026-05-20 et
le 2026-06-16 (102 le seul 2026-06-08) ; « Court-circuit profil » (profils
BACHELIER/PARENT/ETUDIANT_UAM plafonnés à 2 itérations) — **4 occurrences**.
Ces deux mécanismes sont eux aussi **absents des logs depuis le
2026-06-16** — le trafic récent (07-28, 08-05, 08-15, 08-16) ne déclenche ni
la limite dure ni les courts-circuits préventifs.

### Cause identifiée pour les pics récents (2026-08-05)

Le trafic récent n'évite pas les problèmes de latence pour autant : le
2026-08-05 concentre les **53 événements de troncature d'historique**
(`_compress_history`, `"Troncature de l'historique : N → 20 messages"`) de
tout le dossier `logs/`. Deux sessions distinctes de cette journée illustrent
le phénomène, à des échelles très différentes.

**Session `c43d33cf-...` (20:57–21:01)** — ses 3 questions, dont la plus
lente est le maximum absolu de tout l'échantillon `metrics.db` :
```
20:57:33  "Comment s'inscrire en première année ?"        11 962 ms
20:59:44  "je suis un nouveau bachelier..."                30 769 ms
21:01:41  "Je vais m'inscrire en MPC à la FAST"            72 035 ms  ← maximum global
```
soit une latence qui triple à chaque tour de cette conversation, corrélée à
une croissance modeste de l'historique juste avant les deux dernières
réponses (`21:00:29 : 44 → 20 messages`, `21:01:35 : 48 → 20 messages`). Ce
sont, à noter, **3 des questions de cette seule session, dont le maximum
global** — pas les 3 réponses les plus lentes de l'échantillon dans
l'absolu : la 2e et la 3e place globales (47 513 ms et 31 950 ms)
appartiennent en réalité à une autre session, ci-dessous.

**Session `avant-1785960758` (21:12–21:16)** — preuve nettement plus nette,
mise au jour en revérifiant la formulation initiale de cette section : ses 4
dernières questions se dégradent brutalement, de 9 255 ms à 47 513 ms —
```
21:14:53  "Quelles sont les bourses disponibles ?"          9 255 ms
21:15:18  "Comment obtenir ma carte d'étudiant ?"           24 835 ms
21:15:50  "Quel est le calendrier universitaire ?"          31 950 ms
21:16:38  "Quelles sont les filières de la FSEG ?"          47 513 ms
```
et cette dégradation encadre exactement, dans le même log, la séquence de
troncature la plus spectaculaire de tout `logs/` : entre 21:12:54 et
21:16:23, la taille de l'historique avant troncature passe par 32, 35, 74,
76, 156, 158, 320, 644, 647, 1298, 1300, 2604, 2606, 5216, 5220, 10444,
10446, 20896, 20898, 41800, 41802, **83608**, 83610 messages — un
doublement quasi exact à chaque tour, qui reproduit très précisément le
« 1 → 2 → 4 → … → 83 608 messages » cité dans le commentaire de
`graph_nodes.py::route_and_store` (lignes 161-165). Cinq échecs identiques
sont journalisés dans cette même fenêtre (21:13:04, 21:13:10, 21:14:27,
21:14:31, 21:14:51 ; dupliqués dans `errors_20260805.log`, soit 10 lignes au
total — aucune autre journée n'en comporte) :
```
BadRequestError 400 — "messages with role 'tool' must be a response to a
                        preceeding message with 'tool_calls'."
```
`metrics.db` ne montre aucune autre session active entre 21:12 et 21:17 ce
jour-là (`SELECT ... WHERE created_at LIKE '2026-08-05%' ORDER BY
response_time_ms DESC`, rows re-triées par `created_at` — seule
`avant-1785960758` a des questions dans cette fenêtre) : l'attribution de la
séquence de troncature à cette session repose sur cette absence de session
concurrente, pas sur un identifiant explicite dans les lignes de troncature
elles-mêmes (qui ne portent pas de `user_id`).

Avant correction, `route_and_store` renvoyait `{**state, ...}` sans
réinclure `messages`, ce qui faisait repasser l'historique déjà accumulé
dans le réducteur `add` d'`AgentState` et le doublait à chaque tour, avec
pour conséquence des réponses de plusieurs dizaines de secondes et des
erreurs 400 masquées par le repli de `call_model`. Le correctif
(suppression du `{**state}`) est arrivé dans le commit `31abc43`
(2026-08-16, aujourd'hui) — **postérieur** aux deux sessions ci-dessus.
Contrairement à ce qu'on pourrait attendre d'une deuxième session lente le
même jour, celle d'`avant-1785960758` ne nuance pas la corrélation, elle la
**renforce** : elle reproduit le chiffre exact du commentaire du code
(83 608) et n'a aucune session concurrente pour expliquer autrement la
panne — c'est une corroboration plus précise que celle offerte par
`c43d33cf` seule. Cela dit, comme le code exact qui tournait ce jour-là n'a
pas de commit dédié antérieur à `31abc43` (l'historique git n'a été
réorganisé en commits cohérents qu'aujourd'hui, tâche 1), cette causalité
n'a pas pu être re-testée en relançant le code historique lui-même :
**cause fortement corroborée (coïncidence temporelle, signature d'erreur
identique, et progression numérique identique au commentaire du code),
mais non re-reproduite pas-à-pas sur le code historique exact**. Le tableau
