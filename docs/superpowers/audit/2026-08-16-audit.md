### Coût d'import invisible : `document_loader` (10,36 s)

Mesuré en tâche 9 (caractérisation d'`api/agent_service.py`, revu par le
contrôleur après correction du bouchon `sys.modules` de la tâche 9) : un
simple `import api.agent_service` coûte **10,36 s** pour la seule chaîne
`document_loader` → `langchain_text_splitters` → `langchain_text_splitters.
sentence_transformers` → `sentence_transformers` (→ `transformers`, `torch`,
`nltk`, `scipy`…), contre **0,41 s** pour tout le reste du module. Profilé au
`python -X importtime` (détail dans
`.superpowers/sdd/2026-08-16-nettoyage-refactorisation/task-9-report.md`) ;
aucun appel réseau, aucun poids de modèle téléchargé — un pur coût de
chargement de code Python.

Cause : `api/agent_service.py` fait `from document_loader import
load_and_index_documents` au niveau module ; `document_loader.py` importe à
son tour `langchain_text_splitters`, dont le paquet installé importe lui-même
inconditionnellement `sentence_transformers` dans son `__init__.py`.

Ce coût précède le compteur de temps de `get_agent()`
(`api/agent_service.py:69`) : il est donc **invisible dans les logs de
démarrage** et absent de l'estimation « 5 à 15 s » qu'annoncent `run_api.sh`
et `CLAUDE.md`. Il est payé **une fois par démarrage de processus** (le
singleton `get_agent()` n'est construit qu'une fois, mais l'import du module
a lieu dès le chargement d'`api/agent_service.py`, avant même le premier
appel).

**Piste identifiée, non implémentée** — vérifiée par la revue de la tâche 9 :
déplacer `RecursiveCharacterTextSplitter`, `PyPDFLoader`/`DirectoryLoader`/
`TextLoader` et `FAISS` dans le **corps** de `load_and_index_documents()`
(imports paresseux, exécutés seulement quand la fonction est appelée plutôt
qu'au chargement du module), ce qui reporterait le coût de 10,36 s hors du
chemin d'import et le rendrait visible dans les logs de démarrage. Effet de
bord à traiter dans le même geste : l'annotation de retour `-> FAISS` de la
fonction est évaluée à la définition du module, donc avant que `FAISS` ne
soit importé si l'import est déplacé dans le corps — elle devrait passer en
chaîne (`-> "FAISS"`) ou le fichier adopter
`from __future__ import annotations`. **Non implémenté** : c'est un
changement de structure (déplacement d'imports, sémantique d'annotations)
qui mérite son propre cycle plutôt qu'un correctif improvisé en fin de
tâche 12.

`check_question_relevance` (`tools.py:353-442`) ne reconnaît la question des

**Mesure d'impact sur le routage réel** — `check_question_relevance` n'est pas
un outil isolé : c'est lui qui décide, dans `route_and_store`
(`graph_nodes.py:230-236`), si le message part vers `agent` ou vers
`reject_query` (branche générale, atteinte par tout message qui n'est ni une
salutation, ni un remerciement, ni rattaché à un profil spécial). Mesuré en
appelant directement `route_and_store` — le nœud réel du graphe, sans LLM ni
réseau — sur six formulations naturelles de la question la plus commune d'un
candidat :
```
$ venv/bin/python -c "

from graph_nodes import route_and_store

questions = [
    'Quels sont les frais ?',
    'Quel est le montant des frais ?',
    'Je veux connaitre les frais',
    \"Quels sont les frais d'inscription ?\",
    'Combien coûte une inscription ?',
    'Bonjour, quels sont les frais ?',
]
for q in questions:
    state = {'messages': [HumanMessage(content=q)]}
    result = route_and_store(state)
    print(result['routing_hint'], '<-', q)
"

reject_query <- Quel est le montant des frais ?
reject_query <- Je veux connaitre les frais
agent <- Quels sont les frais d'inscription ?
agent <- Combien coûte une inscription ?
agent <- Bonjour, quels sont les frais ?
```
3 formulations sur 6 sont routées vers `reject_query`, qui répond que
l'assistant ne traite que les questions UAM — un échec utilisateur actif et
visible pour la question la plus attendue d'un candidat, sans aucune
condition de configuration à réunir. Note pour la 6ᵉ ligne : au niveau
unitaire, `check_question_relevance("Bonjour, quels sont les frais ?")`

`detect_greeting` classe ce message en `BOTH` (salutation + question), et
`route_and_store` (`graph_nodes.py:231`) court-circuite alors vers `agent`
indépendamment de la pertinence — ce cas précis n'est donc pas impacté en
pratique, seuls les trois premiers le sont.

Ni la forme accentuée ni la forme sans accent ne matchaient avant la
tâche 18 (vérifié sur le commit `fc0f65b`, précédant le correctif) : le
mot-clé accentué `"relevé"` n'était jamais une sous-chaîne littérale de
« relever » (accents différents), et il n'y avait pas de normalisation
pour les rapprocher. Après le correctif de tâche 18, `_sans_accents`
ramène `"relevé"` à `"releve"`, qui **est** une sous-chaîne littérale de
« relever » — un chevauchement entièrement nouveau, sur un mot qui n'a
pourtant aucun rapport avec le document « relevé de notes ».

**Corrigé le 2026-08-17** — quatre itérations sur ce seul mot-clé, chacune
ayant révélé une collision (ou une lacune) que la précédente ne couvrait
pas :

1. Round 1 (commit `1503536`) : le mot-clé isolé `"relevé"` est retiré de
   `keywords_uam` et remplacé par deux tournures en sous-chaîne,
   `"relevé de notes"` et `"mon relevé"`. Referme la collision avec
   « relever », mais perd les formulations génériques — article indéfini
   (« un relevé »), forme nue sans « mon », pluriel (« mes relevés »).
2. Round 2 (commit `7f8511f`) : `keywords_mot_entier`, `"relevé"` cherché
   en mot entier avec pluriel optionnel (`\breleves?\b`). Restaure les
   formulations génériques, mais un mot isolé ne peut pas distinguer le
   nom « relevé » du verbe conjugué « relève »/« relèves » : une fois
   désaccentués, ce sont des homographes exacts (même chaîne « releve »),
   et `\b` ne sépare pas deux chaînes identiques. « Ce village relève de
   la commune de Zinder », « elle relève la tête », « tu relèves un défi »
   redevenaient `PERTINENT` à tort.
3. Round 3 (commit `fdea59e`) : `keywords_mot_entier` redevient une liste
   de tournures à déterminant explicite — `"un relevé"`, `"le relevé"`,
   `"mon relevé"`, `"des relevés"`, `"mes relevés"`, `"relevé de notes"` —
   un verbe conjugué n'étant jamais précédé d'un déterminant. Toujours
   comparées en mot entier (`\b` en tête de motif, pas simple
   sous-chaîne) : une sous-chaîne plate collisionnerait encore, « elle
   relève » contenant littéralement « le relevé » une fois désaccentué
   (« elle » se termine par « le »). Referme la collision d'homographe,
   mais la liste s'avère trop étroite : « les relevés » (déterminant
   « les » absent de la liste) et la forme nue sans déterminant
   (« relevé disponible ? ») redeviennent `HORS_SUJET` à tort — de vrais
   usages d'étudiants, éconduits.
4. Round 4 (commit `02eb677`, **mécanisme actuel**) : retour au mécanisme
   du round 2 (`keywords_mot_entier = ["relevé"]`, `\breleves?\b` sur la
   forme désaccentuée), tranché par le contrôleur sur le principe qu'un
   faux négatif (question légitime éconduite) nuit davantage qu'un faux
   positif (réponse à côté, bénigne). Le faux positif du round 2 sur le
   verbe conjugué homographe est donc **assumé**, documenté en commentaire
   dans `tools.py` et tracé comme dette dans BUG-06 ci-dessous — dernier
   tour sur ce mot-clé.

Couverture de test dans `tests/test_bug_05_accents.py` :
`TestReleveMotEntier` vérifie les formulations génériques (article
défini/indéfini/possessif, pluriel, forme nue — y compris les six
formulations qui ont motivé le round 4) en `PERTINENT`, et que l'infinitif
« relever » reste `HORS_SUJET` (le « r » final bloque toujours la
frontière de mot). `TestFauxPositifsAssumes` documente explicitement, avec
son propre docstring, que le présent de l'indicatif (« relève »/« relèves »)
est désormais classé `PERTINENT` à tort — un compromis assumé, pas un
oubli. `TestPasDeRegression` couvre par ailleurs la collision round 1
(« il fait relever le défi » et deux autres conjugaisons de l'infinitif,
toujours `HORS_SUJET`).

**BUG-06** — mots-clés longs sans borne de mot, sous-chaîne d'un mot sans
rapport :
```

print(c.func(question='Quelle est ton hypothese ?'))

```
`"thèse"` (`keywords_uam`, `tools.py:398`) est cherché par sous-chaîne,
comme tous les mots-clés longs (choix délibéré pour couvrir les formes
fléchies, ex. « inscription » → « inscriptions »). Or « thèse » est
également une sous-chaîne littérale de « hypothèse », « synthèse »,
« antithèse », « parenthèse ». Vérifié sur le commit `fc0f65b` (avant tout
travail de la tâche 18) que la forme accentuée était déjà `PERTINENT` :
ce défaut est donc antérieur à BUG-05 et à la normalisation sans accents.
La normalisation de tâche 18 n'a fait qu'étendre la même confusion aux
saisies sans accent (« hypothese »), sans en changer la nature.

Même défaut de fond que BUG-04 (correspondance par sous-chaîne non
bornée en mot entier), mais BUG-04 ne portait que sur les abréviations
courtes (`abreviations_uam`) ; celui-ci porte sur les mots-clés longs
(`keywords_uam`) que la tâche 17 n'a pas touchés. **Laissé en dette** :
une correction ponctuelle sur `"thèse"` ne traiterait que ce cas, alors
que la même faille existe potentiellement pour d'autres mots-clés longs.
La correction générale — passer `keywords_uam` en recherche de mot entier
avec gestion du pluriel et des formes fléchies — change le mécanisme de
la fonction et mérite sa propre tâche et ses propres tests, plutôt qu'un
correctif improvisé en fin de tâche 18.

D'autres collisions du même type, vérifiées réelles, relèvent de la même
dette : `"cours"` ⊂ « discours », « secours », « parcours » ; `"service"`
⊂ « self-service » ; `"master"` ⊂ « mastermind » ; `"institut"` ⊂
« instituteur », « institutrice ».

**Extension BUG-06 — homographe « relevé »/« relève »** (2026-08-17,
ruling round 4 de BUG-05) : dette de même nature, mais résultant cette
fois d'un choix délibéré plutôt que d'une sous-chaîne non bornée.
`keywords_mot_entier` (`tools.py:393-416`) cherche `"relevé"`/`"relevés"`
en mot entier générique — retenu après trois tours parce qu'une liste
fermée de tournures à déterminant ratait des questions réelles (« les
relevés sont-ils disponibles ? », « relevé svp »). Or, une fois
désaccentué, « relevé » (nom) et « relève »/« relèves » (présent de
l'indicatif de « relever ») forment la même chaîne `releve` : aucune
expression régulière ne peut les séparer sans analyse grammaticale.

**BUG-08** — singleton de configuration figé incomplet par un ordre d'import
précoce (latent, découvert en tâche 10) :

Découvert le 2026-08-21 en tâche 10 (caractérisation en lecture seule de
`database_connector.py`) : le test `is_database_available() is True`
passait quand `tests/test_database_connector.py` était lancé seul, mais
échouait de façon déterministe (100 % reproductible, pas un flake) dans
`venv/bin/python -m pytest tests/ -q` (suite complète). Reproduction
isolée du mécanisme, hors du framework de test :
```
$ venv/bin/python -c "

sys.path.insert(0, os.path.abspath('.'))
import tools   # memory.py, importé par tools.py AVANT database_connector.py,
               # appelle get_config() au niveau module via
               # _user_memory = UserMemory() (memory.py:191)

from database_connector import is_database_available

"
... - app_config - WARNING - Configuration invalide ou incomplète: Clé API
manquante pour le provider 'openrouter': OPENROUTER_API_KEY

```
`app_config.get_config()` (`app_config.py:226-240`) est un singleton
mémoïsé (double-checked locking sur le global `_config`) pour tout le
process. `app_config.py` ne charge jamais `.env` lui-même : parmi les
modules atteignables depuis la suite de tests, seul `database_connector.py`
(ligne 15) appelle `load_dotenv()`. `tools.py` importe `memory` (ligne 28)
avant `database_connector` (ligne 92) ; `memory.py:191` exécute
`_user_memory = UserMemory()` au niveau module, et `UserMemory.__init__`
(`memory.py:21`) appelle `get_config()`. Si ce tout premier appel
process-wide a lieu avant que `.env` soit chargé, `_config` se fige
**entier** — pas seulement `database.db_type` : le `WARNING` ci-dessus
montre que la clé API OpenRouter est elle aussi jugée absente au moment du
figement, alors que `os.environ` la contient bel et bien juste après (elle
a fini par être chargée, seulement trop tard pour ce `get_config()` déjà
mis en cache). Le défaut relève donc de `app_config` (absence de
`load_dotenv()` dans le module lui-même), pas d'une particularité de
`database_connector.py`.

**Latent, jamais déclenché en production** : `agent_uam.py:4`,
`api/main.py:32` et `app_streamlit.py:18` appellent tous `load_dotenv()`
en tout premier, avant tout import applicatif (`api/main.py` porte même
des `# noqa: E402` explicites sur les imports qui suivent, signe que
l'ordre est intentionnel). Le bug ne peut donc pas se déclencher via un
point d'entrée réel — seul l'enchaînement de plusieurs fichiers de test
dans un unique process `pytest` l'expose, en n'appelant jamais
`load_dotenv()` avant le premier import de `tools`/`memory`.

correction ; « tu n'écris que des tests, aucune ligne de code
